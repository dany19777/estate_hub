# EstateHub: путь к полноценному запуску

Обновлено 23.09.2026. Этот документ фиксирует проверенные факты в репозитории, а не обещает готовность к публичному запуску.

## Решения владельца проекта

- Платежи покупателей и платное онлайн-бронирование отложены. Покупатель оставляет заявку на консультацию.
- Публикация вторичного объявления платная **после** одобрения суперадмином. Перевод допускается на счёт компании или указанную банковскую карту. Наличные не принимаются. Факт поступления денег проверяет суперадмин по выписке.
- Подписка застройщика оформляется по подписанному договору и банковскому переводу; суперадмин вручную подтверждает договор и поступление средств.
- Ипотека и банковские интеграции отложены.
- После каждого значимого проверенного изменения выполняются commit и push в GitHub.

## Что реализовано сейчас

- Вторичное объявление остаётся скрытым после одобрения документов. Продавец видит сумму и реквизиты только после проверки, отправляет номер банковской операции. Суперадмин сверяет поступление, подтверждает заявку и только тогда открывает объявление. Публичные выборки дополнительно требуют активный оплаченный период.
- Неоплаченные вторичные объявления, открытые старыми версиями, переводятся в закрытый статус при запуске. Истечение оплаченного периода закрывает публикацию.
- Онлайн-списания в API бронирования, подписки застройщика и продвижения отключены. Покупателю предлагается консультация вместо платного бронирования.
- Застройщик может указать номер подписанного договора и банковского перевода по выбранному тарифу. До сверки заявка остаётся в ожидании. Суперадмин подтверждает или отклоняет заявку с причиной; активация подписки защищена уникальным событием от повторного подтверждения.
- SMS-код стенда возвращается в ответе только при явном `ENABLE_SANDBOX_SMS=true`; для публичного окружения этот флаг не включать.
- Административные изменения требуют платформенную роль поверх конкретного права. Организация с правом управлять собственным биллингом не может подтверждать платежи и управлять продуктами платформы.
- Каждый пункт сайдбара застройщика открывает отдельный раздел. Квартиры, просмотры, сделки, документы, медиа и аналитика читают реальные данные своей организации; подтверждение просмотра и настройка времени ответа сохраняются через API. Владелец или администратор может добавить уже зарегистрированный аккаунт сотрудника и приостановить его доступ.

## Данные и доступы, которые нужны от владельца

| Направление | Что предоставить / подключить | Зачем |
| --- | --- | --- |
| Публикация вторички | Окончательная цена публикации в UZS и срок в днях; официальные реквизиты компании (`PLATFORM_PAYMENT_BANK_NAME`, `PLATFORM_PAYMENT_BANK_ACCOUNT`); при оплате на карту — карта, оформленная для этой деятельности (`SECONDARY_PAYMENT_CARD_NUMBER`, `SECONDARY_PAYMENT_CARD_HOLDER`) | Выставлять точный счёт. Значения задаются как переменные окружения Cloudflare, не записываются в Git. Суперадмину нужен доступ к банковской выписке для сверки номера и суммы операции. |
| Подписка застройщика | Тарифы и лимиты, договор с застройщиком, те же реквизиты компании, регламент кто проверяет подписанный договор и банковский перевод | Включать и продлевать подписку только после ручного подтверждения. Номер договора, операции и решение сохраняются в аудите. |
| SMS / телефон | Договор и API-доступ к SMS-провайдеру, разрешённое имя отправителя, тариф и тестовый номер; домен и callback при необходимости | Доставлять OTP вне сайта. До подключения нельзя считать телефон подтверждённым в публичном окружении. |
| Проверка личности | Выбранный провайдер eKYC с API и договором **или** утверждённый ручной регламент: кто проверяет, какие документы допустимы, срок хранения, основания отказа | Нынешний провайдер создаёт только ручной sandbox-кейс и не сверяет подлинность документа. |
| Инфраструктура | Продакшен-аккаунт Cloudflare с доступом к Workers, D1, R2, DNS; домен; отдельные preview/prod окружения; политика резервного копирования | Развернуть проект, хранить данные и медиа, восстановиться после ошибки. |
| Уведомления и поддержка | Рабочий домен почты, адрес поддержки, `RESEND_API_KEY`, подтверждённый sender; шаблоны писем на RU/UZ/EN | Доставлять вопросы с сайта и важные статусы заявок. |
| Политики | Утверждённые правила публикации, обработки персональных данных, оферта для платной публикации, политика возвратов и сроков | Без этого платную публикацию нельзя считать полностью готовой для публичных пользователей. Юридические тексты должен утвердить специалист владельца. |

## Проверки и оставшаяся работа

1. **Покупатель.** Пройти вручную все RU/UZ/EN сценарии: вход, избранное, сравнение, уведомления, запись на просмотр, обращения, поддержка. Удалить оставшиеся обещания платной брони. Подключить реальные SMS и KYC, затем проверить ограничения частоты и восстановление доступа.
2. **Застройщик.** Проверить создание ЖК и квартир, модерацию, CRM, лимиты, права сотрудников и уведомления. Разделы документов и медиа показывают уже сохранённые материалы; безопасная загрузка файлов и приглашения по почте ещё не подключены. Договорная подписка с ручной оплатой реализована, но нуждается в реальных реквизитах и полном E2E-тесте. Новые платные продвижения пока отключены.
3. **Суперадмин.** Матрица платформенных прав и отклонение платежных заявок добавлены; ещё нужны динамические тесты ролей, отчёты по оплатам/отменам, проверка отзывов и жалоб, экспорт для сверки и MFA.
4. **Бронирование.** В БД есть уникальный частичный индекс `idx_reservations_one_active_listing`, который запрещает две активные брони одной квартиры. Маршруты бронирования сейчас выключены. Перед будущим включением настоящих платежей устранить разделение подтверждения оплаты на две транзакции в `app/api/reservations/[id]/confirm/route.ts`, провести конкурентный и отказоустойчивый тест с реальным провайдером.
5. **Безопасность и эксплуатация.** Добавить MFA для суперадминов, мониторинг ошибок и подозрительных действий, проверку доступа на всех API и E2E-тесты трёх ролей, резервное копирование/восстановление D1 и сканирование зависимостей. Статический просмотр mutation-API не выявил маршрутов без явного механизма авторизации, кроме публичных login/logout/support, но это не заменяет динамический тест прав.
6. **Проверка запуска.** Полный staging-цикл со всеми тремя ролями, мобильный UX, доступность, нагрузка, формы и почта; затем отдельный запуск в production. Ипотека, банки и платежи покупателей остаются вне этого этапа.

Оплата публикации подтверждается человеком по банковской выписке. Введённый продавцом номер операции сам по себе **не является** доказательством оплаты.
