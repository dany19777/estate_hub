# Проверка EstateHub по чек-листу безопасности

Дата: 29.09.2026. Основа: `ai_agent_review.md`, предоставленный владельцем. Проверены маршруты API, схема D1, серверные права и основные внешние вызовы. Это анализ кода и локальные проверки, а не независимый пентест или подтверждение готовности production-окружения.

| Пункт | Вывод и доказательство | Остаточный риск / действие перед запуском |
| --- | --- | --- |
| IDOR/BOLA | **Частично подтверждено.** `lib/auth.ts` проверяет сессию, MFA, роли и права. Выборки покупателя ограничены `user_id`, застройщика — `organization_id`; чтение аудита, финансов, биллинга, продвижения, отзывов и справочника дополнительно ограничено соответствующими правами. Очереди модерации и верификации не выдаются ролям без права обработки. `check:roles` и `check:orgs` проверяют известные сценарии. | Проверить все действия с конкретными ID в E2E для всех платформенных ролей после MFA и двух компаний. Smoke-тесты не доказывают отсутствие IDOR во всех маршрутах. |
| Валидация, SQL-инъекции, XSS | **Частично.** Значения SQL передаются через D1 `.bind()`, динамические фрагменты запросов собраны из констант. React экранирует текст; HTML письма экранируется в `lib/support-mail.ts`. Форма поддержки ограничена 8 KiB, проверяет типы и длины. | В других маршрутах используется ручная валидация; общей схемы для каждого body/query/params и общего ограничения размера тела нет. Провести fuzz-тест форм и параметров. |
| Секреты | **В отслеживаемом коде не обнаружены известные форматы ключей.** Пароли тестовых аккаунтов хранятся в игнорируемом `work/`; секреты — в окружении. Тестовые аккаунты теперь создаются и могут входить только на локальном hostname при настроенном тестовом окружении. | Убрать тестовые секреты из production, хранить ключ MFA и API-ключи в секретах Cloudflare, ротировать ранее переданные через чат токены и проверить фактическое окружение. |
| Rate limiting | **Частично.** Вход и MFA используют атомарные счётчики D1; SMS имеет интервал и лимит попыток. Форма поддержки, заявки на консультацию и переписка обеих ролей теперь также ограничены атомарным счётчиком D1. | Нет общей политики для остальных мутаций и тяжёлых чтений. Нужны правила Cloudflare WAF/Rate Limiting и нагрузочная проверка. |
| Connection pooling | **Не применимо к текущему драйверу.** Сервер использует binding Cloudflare D1 (`env.DB`), а не самостоятельно создаёт SQL-соединение на каждый запрос. | Проверить лимиты D1 и поведение под нагрузкой в staging; собственного пула не добавлять. |
| Stateless / локальное состояние | **В основном выполнено.** Сессии, сообщения, заявки и счётчики лежат в D1; `.wrangler/state` используется только стендом. Кэш курса и promise инициализации ограничены одним значением на экземпляр. Создание схемы и демоданных теперь включается только через `ESTATEHUB_SEED_DEMO=true`; production требует миграций. | R2 для файлов ещё не подключён. Применить миграции к отдельным staging/prod D1 и проверить отсутствие флага демоданных в production. |
| Утечки памяти | **Очевидного неограниченного глобального накопления не найдено.** Постоянных массивов пользовательских сессий нет; кэш курса перезаписывается одним объектом. | Проверить память Worker при нагрузке и реальных объёмах каталога. |
| Гонки | **Частично.** Уникальный индекс `idx_reservations_one_active_listing` запрещает две активные брони одной квартиры; D1 batch и уникальные ключи защищают другие критические записи. Оплачиваемая бронь выключена. | Перед реальными платежами объединить подтверждение оплаты и смену статуса в согласованную операцию с провайдером; провести конкурентный тест. Проверить одновременные модерации и ручные подтверждения офлайн-платежей. |
| Ошибки | **Частично.** Клиент получает короткие безопасные сообщения без stack trace; ошибки авторизации отделены от 500. Не все маршруты пишут внутреннюю причину и контекст в лог. | Подключить сбор ошибок и алерты; унифицировать серверное логирование без персональных данных и секретов. |
| Fallbacks / retries | **Частично.** ЦБ: таймаут 4 секунды, одна повторная попытка. Почта: таймаут 8 секунд, неотправленные вопросы сохраняются в D1; сотрудник может повторить отправку с тем же ключом провайдера. | Проверить реальный Resend и сценарии потери ответа в staging. Платежный fallback пока не требуется, потому что онлайн-платежи отключены. |
| Идемпотентность | **Для проверенных критических путей.** Брони, платежные заявки, заявки на консультацию, форма поддержки и сообщения имеют ключи повтора; БД ограничивает дубликаты. Повтор поддержки и сообщений возвращает исходную запись, повтор с другим содержимым отклоняется. | Не все пользовательские мутации требуют ключ; перед включением новых денежных операций проверять их отдельно. |

Локально проверено: `pnpm check:migrations` (30 файлов), `pnpm check:roles` (177 ответов), `pnpm check:orgs`, `tsc --noEmit`, production-сборка. Форма поддержки: исходный запрос 202, повтор 202 с тем же ID, изменённое тело 409, шесть параллельных запросов дали четыре 202 и два 429 после одной предыдущей попытки. Сообщения покупателя и застройщика: создание 201, повтор 200 с тем же ID, изменённое тело 409. Тестовые записи удалены из локальной D1.
